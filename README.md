Prowler CSPM Triage Pipeline
A Python tool that reads Prowler's raw CSPM output and transforms it into an actionable, deduplicated triage report, because 80 findings is noise, not signal.

Result: 80 raw findings collapsed into 16 unique problems, ranked by severity, with affected-resource counts.
The Problem
Prowler is a widely used open-source cloud security scanner. It runs hundreds of checks across AWS services against frameworks such as CIS, NIST, PCI-DSS, and HIPAA. It is excellent at finding misconfigurations.

But a raw scan of a real AWS account can produce hundreds of findings. My account produced 80 critical/high failures in a single scan.

A security team cannot fix 80 things on Monday morning. They need to know:
Which problems matter, and how many resources does each one affect?

That is what this tool does.
What This Tool Does
1. Reads Prowler's OCSF JSON output.
2. Filters to FAIL findings only.
3. Groups findings by check ID, so 17 GuardDuty findings across 17 regions become one problem with 17 affected resources.
4. Ranks findings by severity, then by the number of affected resources.
5. Produces a clean top-10 triage report.
Input: Prowler OCSF JSON (output/*.ocsf.json)

Output: Ranked triage report in the terminal.

Quick Start
1. Install Prowler
pipx install prowler
2. Run a Scan
Run a scan for critical and high severity failures:
prowler aws \
  --status FAIL \
  --severity critical high \
  --output-formats json-ocsf
3. Run the Triage Tool
Process the generated JSON output:
python scripts/triage.py \
  --input "output/*.json" \
  --top 10
The tool generates a prioritized triage report directly in the terminal.

What I Learned
1. Prowler Check Titles Describe the Secure State
A check's title can be confusing if you do not understand how Prowler reports results.

For example, a check named "Root account has no active access keys" fails when the root account does have active access keys.

Understanding the secure condition behind each check is essential for interpreting findings correctly.
2. The Real Service Name Is Not in metadata.product.name
That field identifies the scanner as Prowler, rather than the actual AWS service.

The service category used by this project is extracted from:

finding_info.analytic.category

For example: iam, s3, or guardduty.

This distinction matters when grouping findings and generating service-level summaries.
3. Deduplication Is the Core Value of Triage
Prowler can report findings across multiple resources and regions.

A single misconfiguration affecting GuardDuty across 17 regions can produce 17 separate findings.

Grouping by check ID consolidates those findings into a single problem, with an affected-resource count.

Without deduplication, the report is just a list. With deduplication, it becomes a triage tool.
4. Prowler Cloud Already Offers These Capabilities
Prowler Cloud offers triage capabilities and additional functionality, including workflows for false positives, accepted risk, dashboards, and integrations.

This project is a minimal implementation of core CSPM triage concepts, built to understand how security findings analysis works under the hood, not to replace the broader product.
Honest Limitations
- No historical tracking: Each run is independent. There is no comparison of what changed since the previous scan.
- No false-positive handling: Every FAIL is treated as an issue requiring investigation.
- No auto-remediation: The report identifies problems, but remediation is manual.
- No notifications: The report prints to the terminal. Slack notifications are a potential future improvement.
- AWS only: This implementation focuses on AWS findings, even though Prowler supports additional cloud providers.
- Check-level grouping: Findings grouped by check ID may represent different underlying causes or contexts. Grouped findings should be validated before treating them as one remediation task.
